# Common part of the I1 work orders run in parallel (owner's decision 2026-11-19)

Every I1 writer order from I1-3 on includes this text. Up to four agents run at the same time in the one shared checkout on `add-test-suite`.

1. **Read first** (in addition to the order's own list): `CLAUDE.md` (rules, "Integration track"), `Firmware/Tests/README.md`, `Tests/Integration_Tests/claude/charters/I1_WORK_ORDERS.md` (**"Rules common to all I1 work orders" apply to you**, and your WO's row), the charter `Tests/Integration_Tests/claude/charters/F1_TMC4671_CHAIN_REQUIREMENTS.md` (your group, "Oracles", candidate seams), `Tests/Integration_Tests/claude/plans/PROGRESS.md` (registers IB / INR, decisions log), `Tests/Integration_Tests/claude/plans/HANDOFF.md` (I1 rules: set `axis.0.power` and `axis.0.fxratio` first because of IB 7 / bug 23; never a REQUIRE inside an INFO / CAPTURE expression: doctest deadlocks). The helpers you use, read-only for you: `Firmware/Tests/Integration_Tests/support/{FfbHost,PositionScript,IntegrationFixture,ChainScheduler,PidReportBuilder}.h` and `claude/cases/test_f1_hid.cpp` (its `HidFixture` and F1-H1 cases show how to create, send and observe an effect; copy the pattern into your own file, do not include or edit that file).
2. **Your files only**: you may create or edit only the files in your `Tests/Integration_Tests/claude/charters/wo/<ID>.files` (one test file). Other writers are editing other files in the same working tree at the same time: never edit, format, stage, revert or "fix" a file outside your list, even if it looks broken. **Support code is not yours**: if you need a helper that `FfbHost` / `PositionScript` / `TorqueTrace` / the fixture does not offer, write the minimum as a local helper in an anonymous namespace of your test file; if that is impossible (it needs a change of shared code), stop and report under "Lead decision needed". No shared code (`Code_Coverage/`, firmware) may change.
3. **Gate**: `python3 -B Firmware/Tests/Integration_Tests/tools/it_gate.py --wo <ID> --variants default,m32 --own-build` (your own build folders `../ffb-test-build/it-<ID>-<variant>`). Changed files of the other active WOs appear as `other_active`: that is expected. If the build fails in a file that is not yours, wait a little (another writer is mid-edit; re-run up to three times a few minutes apart, never with `sleep` in a test) and report it if it persists; do not touch that file. Write cmake / build paths literally (the hook does not expand shell variables). Stage nothing, commit nothing: the lead commits after a final gate in the shared folders.
4. **Oracles**: PID 1.01 (`Tests/Code_Coverage/shared/specs/USB_PID1_01.pdf`), the TMC4671 datasheet (`TMC4671-LA_datasheet_Rev2.07.pdf`), MATH written out in a comment; absolute counts from firmware constants are HD: always `characterization:` with `// INR <ID>/<k>: ...`. **Torque sign of a polar direction**: PID 1.01 5.1 defines no polar zero. Do not copy the sign the firmware produces as a plain expectation: state in a comment which PID property you rely on (reversal over 180 degrees, restoring / opposing for conditions relative to the *displacement* or *motion* the test scripts, which needs no polar zero), and put the absolute direction-to-sign mapping into one `characterization:` case of your file citing "polar zero undefined, PID 1.01 5.1; reconciled by the lead". The lead compares the four files before the commits.
5. **Defects**: confirm in the firmware source (file:line) and with a failing test of the intended behaviour, `KNOWN_ISSUE("(IB <ID>/<k>) ...")` with `REQUIRE_CHAIN_MODELLED()` right before the defect assertion (first failing assertion = the defect; check in both builds); a coverage bug hit again: `(IB <ID>/<k>; same as bug <m>)` (search `Tests/Code_Coverage/claude/reports/BUG_REPORT.md` and `Tests/Integration_Tests/claude/reports/BUG_REPORT.md` first: an integration bug already registered, e.g. IB 7, is cited by its number, not re-labelled). The lead assigns final numbers.
6. **Every case**: `IT_DELETES_FFBHIDMAIN`, bring-up through the fixture, `setSpiFrameUs(0)` after bring-up unless the case is about frame time, one behaviour per case, name `F1-<id>: <statement>` or `characterization: [F1-<id>] <statement>`; equal results in default and m32 (flag any float-to-int conversion that can go out of range for a reachable setting: F1-B2 input). Also run your file's cases once with `-s` under `timeout -s KILL 300` from your own build folder (they must finish).
7. **Report**: write a short status to `/tmp/claude-1000/-mnt-SATA-SSD1-OpenFFBoard-Testing-OpenFFBoard/bbf099dc-2ff5-438b-bef8-129a2ca24312/scratchpad/<ID>_status.md` early and keep it current. Turn limit 80: within about 10 turns of it, stop and deliver your report (partial if needed). Answer format: your file with a one-line summary; per requirement the cases and their oracle; the observed values that matter (as ratios where the assertion is a ratio); the sign / polar-zero characterization and what it observed; every `KNOWN_ISSUE` / `characterization:` case with its provisional label and firmware evidence; float-to-int conversions noticed; anything under "Lead decision needed". The last line must be the gate's last line exactly as printed.
