### What to build

1. **F1-H2: one case per output report type the descriptor declares** (Set Effect, Set Envelope, Set Condition, Set Periodic, Set Constant Force, Set Ramp Force, Effect Operation, Block Free, Device Control, Device Gain; build the list from the descriptor, and name any declared output report you do not cover with the reason). Each case is a smoke test of one report's effect at the chip in the direction its PID section defines: e.g. Set Constant Force with a larger Magnitude raises |torque| (5.6); Device Gain lower reduces |torque| proportionally (5.10, ratio only); Set Envelope with Attack Level 0 makes the torque start below the steady value (5.2); Set Condition gives a spring force once the position is displaced (use `PositionScript`, 5.3; sign only: a restoring direction at the chip is the I1-5 / I1-7 subject, here only "non-zero and reversing with the displacement"); Set Periodic gives a torque that changes over one Period (5.5); Set Ramp moves the torque between Start and End (5.7); Effect Operation start / stop (5.9); Block Free removes the effect's torque (5.11.2). Keep each to the PID property, no absolute counts (those are I1-3 to I1-6); mention in a comment which later WO checks it quantitatively.
2. **Device Control encoding (part of F1-H2 / F1-H4)**: send each Device Control command with `PidReportBuilder::deviceControl` (PID 1.01 Figure 16: one command byte whose value is the command's position in the descriptor's usage list plus the logical minimum, 1..6) and check the behaviour PID 5.13 gives each one at the chip and in the PID State report: DC Enable Actuators, DC Disable Actuators (torque 0, Actuators Enabled false), DC Stop All Effects (torque 0, effects stopped but still allocated: a later Effect Operation Start of the same index works), DC Device Reset (effects freed: Block Load / Pool behaviour after it, PID 5.13), DC Device Pause (torque 0, Device Paused true) and DC Device Continue (torque back). The firmware's own comment at `Firmware/FFBoard/Src/HidFFB.cpp:113` reads the byte as bit flags (1, 2, 4, 8, 16, 32): compare with the PID encoding, and if a command does the wrong thing because of it, that is a test of the PID behaviour with `KNOWN_ISSUE("(IB I1-2/<k>) ...")`. Do not change the builder's encoding to match the firmware.
3. **F1-H4 (P2): PID State input report** (5.12; decode with `FfbHost::states()` / `latestState()`): Actuators Enabled after DC Enable / Disable, Device Paused after Pause / Continue, Effect Playing after Effect Operation Start / Stop as far as the descriptor declares it (INR 2: no Effect Block Index in the report, so "which effect" cannot be asserted; cite INR 2), Actuator Power / Safety Switch as declared. Expected flag values come from PID 5.12 / 5.13; where PID does not fix when the device must send a state report, assert the latest captured report after the action and say so. A state report that should come and does not is a finding (if the IN endpoint is busy with the joystick report the host still polls: the host drains before every transfer since I1-1; if a report is still lost, find out why before calling it a firmware defect).
4. **F1-H5 (P2): robustness on the interrupt OUT endpoint** with `FfbHost::sendRaw`: while a constant force runs at a steady torque, send (a) a report shorter than its declared length, (b) one longer than its declared length (within the endpoint's wMaxPacketSize and also longer than one packet if the endpoint allows), (c) a report ID the descriptor does not declare for output, (d) a zero-length packet; after each: the endpoint is not stalled (handshake ACK or NAK, never STALL), the steady torque at the chip is unchanged over the next 10 FFB cycles, no teardown fault, and a following valid report (e.g. a new Magnitude) works. The PID / HID oracle: HID 1.11 and PID 7 fix the report lengths; what a device must do with a wrong-length report is not specified: the plain test asserts only "no change to the running effect, endpoint usable" (the charter's requirement); anything firmware-specific beyond that is `characterization:` with `// INR I1-2/<k>`. A short report that the firmware `memcpy`s past its length (reads stale bytes) is a defect (IB) if it changes the torque; under ASan an out-of-bounds read would be `KNOWN_ISSUE_UB`.
5. **F1-H6: reports sent within one ms act together in the next FFB cycle.**
   - Add to `FfbHost` a way to put OUT reports on the bus without pumping (`queue(report)`: `hidWrite` only), so that the scheduler's own USB step processes them, and to `ChainScheduler` an option that moves step (a) (USB) after step (c) (FFB) in each step (`setUsbAfterFfb(bool)`, default false; document it in the header's order list). Both are for F1-H6 only.
   - Case 1 (default order): a running constant force effect; queue Set Effect (new direction) and Set Constant Force (new magnitude) for it within the same ms, advance: the first FFB cycle that shows any change shows both (torque equals the value of the new pair, never an intermediate value with only one of the two applied; derive both candidate values as ratios of the previous steady torque).
   - Case 2: the same with `setUsbAfterFfb(true)`: the pair still acts together (in the cycle after), so the result does not depend on the host order (plan 3.3 step 4).
   - Case 3: a pair split over two ms (first report, one FFB cycle, second report) shows the intermediate state for exactly the cycles in between: proves the test can see a half-applied pair, so cases 1 and 2 are not vacuous.
   - Limit (state in the case comment, S11): no preemption, so a report arriving in the middle of `calculateEffects` on the target is not modelled.
