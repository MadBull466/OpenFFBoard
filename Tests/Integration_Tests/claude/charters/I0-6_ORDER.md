### What to build

1. `support/HidReportDescriptor.{h,cpp}`: a parser of HID report descriptors per HID 1.11 §6.2.2: short items (data size 0/1/2/4, sign extension of logical / physical values where HID 1.11 says so), long items (skip, but recognise), main items (Input / Output / Feature with their flag bits, Collection / End Collection), global items (Usage Page, Logical / Physical Min / Max, Unit Exponent, Unit, Report Size, Report ID, Report Count, Push / Pop), local items (Usage, Usage Min / Max, with extended 32-bit usages, delimiters may be rejected as unsupported). Result: per report (type input / output / feature, report ID) the list of fields with usage page + usage (or usage range), bit offset (after the report ID byte), size, count, logical min / max, flags (constant, variable, ...), and the collection path (usage of each enclosing collection) so a field can be found by "report usage + field usage". Report byte length = report ID byte + ceil(total bits / 8). Malformed descriptors (unbalanced collections, report size 0 with count, a report ID 0, data past the end) are errors, not guesses.
2. `support/PidReportBuilder.{h,cpp}`: builds output and feature reports by PID usage names / IDs from PID 1.01 (e.g. Set Effect Report, Set Envelope, Set Condition, Set Periodic, Set Constant Force, Set Ramp Force, Effect Operation, Block Free, Device Control, Device Gain, Create New Effect / Block Load, PID Pool, PID State): the caller names the report and sets fields by usage with values in logical units; the builder places the bits per the parsed layout, little-endian per HID 1.11, and returns a byte vector of the descriptor's length. Strict: a value outside the field's logical range, an unknown usage, or a field of the wrong report is a test failure (not clamped). Also the reverse (decode an input / feature report into usage -> value) for the PID State and Block Load / PID Pool reports the device sends. Take every PID usage ID from the PID 1.01 document and cite the table / page next to it.
3. `IntegrationFixture`: a helper that reads the HID report descriptor from the enumerated device through the simulated host's control transfer (standard GET_DESCRIPTOR, descriptor type Report 0x22, interface recipient, HID 1.11 §7.1.1, length from the HID descriptor's wDescriptorLength of the configuration descriptor) and returns the bytes. Use the `UsbHost` API; if it lacks a needed request, stop and report.
4. Tests:
   - `claude/cases/test_f1_support.cpp` (new): self-tests of the parser and builder on descriptors written by hand from HID 1.11 (its examples, e.g. the joystick / keyboard examples in the appendices, cite the page) and on small synthetic descriptors whose expected parse result is derived by hand in a comment: item sizes, sign extension, push / pop, usage ranges, report IDs, bit offsets across byte boundaries, multi-report descriptors, each malformed case. Builder: a report built from a hand descriptor equals hand-computed bytes; out-of-range values fail.
   - `claude/cases/test_f1_setup.cpp`: **F1-A2** with `IntegrationFixture`: the descriptor read over USB parses without error; every PID report that PID 1.01 defines for a force-feedback device of this kind and that the firmware declares is found with its usage, type and fields (list which PID reports the descriptor declares, by usage, and which PID 1.01 reports it does not declare; asserting the set that PID 1.01 makes mandatory, citing the section; optional ones only reported); for each output / feature report the builder produces a report whose length equals the descriptor's length; the device's input State report (the PID State usage) is found. Report IDs are the firmware's choice: record them in the test as found in the descriptor, do not hard-code them as oracles.
   - Names are statements, with the requirement id in front for F1-A2.
5. `integration.cmake`: add the new sources and test file only.
