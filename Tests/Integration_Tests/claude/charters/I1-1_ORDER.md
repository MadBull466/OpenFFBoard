### What to build

1. **`support/FfbHost.{h,cpp}`**: the host's PID side for an `IntegrationFixture` (constructed with a reference to it, after `bringUp()`):
   - reads and parses the report descriptor over USB once (as `DescriptorFixture::load` does; REQUIRE success) and owns a `pid::PidReportBuilder` for it; `builder()` / `descriptor()` accessors;
   - `CreateResult createEffect(uint32_t effectTypeUsage, ...)`: builds Create New Effect (feature) with the builder, sends it with a control SET_REPORT (feature type 3, report ID from the descriptor, HID 1.11 7.2.2), runs the USB step, then a control GET_REPORT of PID Block Load (7.2.1, wLength = the descriptor's report length) and decodes it with the builder: Block Load Status (which selector), Effect Block Index, RAM Pool Available as the descriptor declares it (IB 4: it is declared as an Array; decode by the declared field type and expose the raw value, do not "fix" it); every handshake checked;
   - `send(const pid::PidReport &)`: interrupt OUT (`hidWrite`), REQUIRE an ACK, then the USB step so the report is processed before the caller advances time (document exactly which scheduler step processes it, and so in which FFB cycle it can first act);
   - `PoolResult getPool()`: GET_REPORT PID Pool, decoded (RAM Pool Size, Simultaneous Effects Max, Device Managed Pool, Shared Parameter Blocks, as declared);
   - PID State capture: change `IntegrationFixture::drainHidIn` so it keeps every input report it takes (by report ID) instead of discarding it; `FfbHost` gives the decoded PID State reports (latest and all since a mark). Draining behaviour and IB 3's dedicated case stay unchanged;
   - config helpers: `command(line)` that sends a CDC command and REQUIREs an OK (non-error) reply, returning it; `getValue(line)` returning the parsed integer of a get command. Find the reply format in the firmware (cite the line) rather than guessing.
2. **`support/PositionScript.{h,cpp}`**: a scripted 0x6B position source for open-loop cases, on scheduler step (f) (the slot the plant uses: attaching a script while a plant is attached, or the reverse, is a fixture fault reported by `firstFault()`). Sources: constant count, ramp (counts per ms from a start), sine (amplitude, period, phase), arbitrary `std::function<int32_t(uint64_t us)>`. It writes `chip1` 0x6B through `setReg` at the end of each step, so the firmware reads the new value in the FFB cycle of the next step: state this order in the header and prove it in a self-test (a step change written in step k is first seen by the axis in the cycle of step k+1). Values are signed 32-bit PhiM counts (DS 0x6B, s32; 65536 per mechanical revolution, cite the datasheet page). Fixture helper `attachPositionScript(PositionScript&)` / detach, with the same lifetime protection as `attachPlant` (a destroyed script is forgotten).
3. **`TorqueTrace`** (in `FfbHost` or its own header in `support/`, your choice, listed in `.files` already if it is in `FfbHost`; if you need a new file, stop and ask the lead to extend the list): one sample per FFB cycle, keyed by `ffbCycles()`: cycle index, simulated time (us), torque and flux at the chip (0x64 decoded, DS 0x64: flux [15:0], torque [31:16]), number of 0x64 writes in that cycle. A cycle without a write keeps the last value (the driver writes only on change). Steps without an FFB cycle (IB 1: about one per 1000 ms) produce no sample. Start / stop, `samples()`, and helpers `torqueAt(cycle)`, `steadyValue(fromCycle, toCycle)` (REQUIREs all equal), `writesPerCycleMax()`.
4. **Self-tests** in `claude/cases/test_f1_support.cpp` (name prefix `support:`; they need not bring up the chain where a stub chip and scheduler suffice, but if they do bring it up they carry `IT_DELETES_FFBHIDMAIN`): PositionScript ramps / sine values per step and the "seen in the next cycle" order; the plant / script exclusivity fault; TorqueTrace sampling with no write, one and two writes in a cycle and a step without an FFB cycle; FfbHost decoding on hand-built Block Load / Pool byte strings with the expected values derived from the descriptor in a comment.
5. **F1-H1 and F1-H3** in a new `claude/cases/test_f1_hid.cpp`:
   - **F1-H1**: Create New Effect for every effect type the descriptor's Create New Effect report can select returns Block Load Success and an Effect Block Index within the declared logical range; successive creates return distinct indices; a later output report addressed to the returned index acts on that effect (minimal proof: a Set Effect + Set Constant Force to that index, Effect Operation Start, and the torque at the chip becomes non-zero with the sign PID 5.1 / 5.6 gives for the direction you choose; derive the sign in a comment). A Block Free of the index makes it available again (PID 5.11.2).
   - **F1-H3**: create effects until Block Load reports Full (or Error); the number of successful creates equals Simultaneous Effects Max of the Pool report (PID 5.11.1), or, if the Pool does not declare it, the number the descriptor's index range allows; the failing Block Load's Effect Block Index and RAM Pool Available are recorded: PID 1.01 section 9 (an example, not a rule) shows index 0 on failure, outside the declared range 1..40 (INR 4 / IQ11, still open): assert only what PID 5.11.2 states as a rule and put the observed index in a `characterization:` case that cites INR 4 (no new INR number for it). RAM Pool Available: assert what PID 5.11.2 says it means; IB 4 makes the declared field an array: if the value cannot be read as a count because of IB 4, the case is `KNOWN_ISSUE("(IB 4) ...")` with `REQUIRE_CHAIN_MODELLED()` first, not a new bug.
   - Any other suspected defect: a test of the intended behaviour with `KNOWN_ISSUE("(IB I1-1/<k>) ...")`; firmware-only values: `characterization:` with `// INR I1-1/<k>: ...`. The lead assigns the final numbers.
6. `integration.cmake`: the new support sources only.
