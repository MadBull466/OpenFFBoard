## Rules common to all I1 work orders

1. **Host side never uses firmware structs or headers for reports.** Every report is built by `PidReportBuilder` from the descriptor read over USB; feature reports go through control SET_REPORT / GET_REPORT (`UsbHost::control`, HID 1.11 7.2.1 / 7.2.2), output reports through the interrupt OUT endpoint (`UsbHost::hidWrite`).
2. **Settings only through the real commands** over CDC (`axis.0.power=`, `fx.0.spring=`, `tmc.0.invertForce=` ...): the user's path. Nothing private is called.
3. **Observation at the chip**: torque / flux = register 0x64 of `chip1` (DS 0x64: flux [15:0], torque [31:16], s16 each), sampled once per FFB cycle (the driver writes 0x64 only on change, `Axis.cpp:488-495`, so a cycle without a write keeps the last value). Axis metrics through `axis.0.curpos` / `curspd` / `curtorque` only where the chip cannot show them.
4. **Oracles** (charter "Oracles" table): PID 1.01 for signs, ratios, shapes, timing of effects (plain tests); DS for register layouts; MATH for derivations written in a comment; **HD (absolute scale from firmware constants) is always `characterization:` + an INR row**. A typical case asserts the PID property as a plain test (sign, linearity as a ratio, period, shape) and, in a separate `characterization:` case, the absolute count at 0x64.
5. **Steady state**: where a filter or limiter shapes the first cycles (constant-force filter, fade-in, slew limiter), the case states the settling rule it uses and why (from the setting, not from observed output).
6. **Defaults visible**: every case sets the settings its expected value depends on (power, fxratio, degrees, gains, inversions) or states the default it relies on with its source line.
7. **Markers**: a suspected defect is a test of the intended behaviour with `KNOWN_ISSUE("(IB I1-<n>/<k>) ...")`; a coverage bug hit again is `KNOWN_ISSUE("(IB I1-<n>/<k>; same as bug <m>) ...")`. Provisional labels `IB I1-<n>/<k>` and `INR I1-<n>/<k>` are replaced by the lead's final numbers (next free: IB 5, INR 5, IQ 12) in the fix round before the commit, so the registers have no gaps. `REQUIRE_CHAIN_MODELLED()` right before the defect assertion. Candidate seams S1-S12 are confirmed in the source and by a failing test before they get a number.
8. **Every case** brings up the chain with `IntegrationFixture::bringUp()` (or the I1-1 helper on top of it), carries `IT_DELETES_FFBHIDMAIN`, and after bring-up sets `setSpiFrameUs(0)` unless the case is about frame time.
9. **Both builds**: torque sequences equal in default and m32 (F1-B1); any float-to-int conversion that can go out of range for a reachable setting is listed in the writer's answer (F1-B2 input for I5).
10. **Names**: `F1-<id>: <statement>` or `characterization: [F1-<id>] <statement>`; one behaviour per case.

## Scope notes and decisions taken in this draft (for the owner)

* **Test files per group, split in two for G-E**: the plan (3.2) names `test_f1_effects.cpp`; I1 uses `test_f1_effects.cpp` (E1-E4, E10, E11) and `test_f1_conditions.cpp` (E5-E9, E12-E14) so that each review sees one subject. `test_f1_hid.cpp` and `test_f1_axis.cpp` as planned.
* **No new shared fake edits expected.** I1-1 edits integration support only. If a writer finds a defect in a shared fake under `Code_Coverage/`, it stops; the fix goes through the override (audit, list of changed coverage results, owner approval, `APPROVED_SHARED_EDITS.txt`).
* **F1-E9 on a one-axis wheel**: the Y block can only be shown not to act on axis 0; the two-axis case belongs to a two-axis main class, which is not on the F1 chain (recorded as a limit in the I1 report).
* **F1-X2 encoder direction**: with the integrated encoder (the fresh-flash bring-up) the reachable direction setting is whatever the TMC / axis commands offer; the external-encoder variant belongs to F1-T9 (I2).
* **F1-X5 and the s32 range**: the 0x6B values are scripted, so the test can jump to the ends of the range; whether the chip can reach them within a session is a DS question answered in the case comment.
* **Position script vs plant**: open-loop cases never attach `WheelPlant`; closed-loop expectations wait for I4.
* **P2 requirements (H4, H5, E13, E14)** are planned as tests, not reasoned out.
* **Order**: I1-1 first (everything uses its helpers); then I1-2 to I1-8 in the table order; I1-5 needs the sign conventions settled in I1-3.
