## Background and owner's decision (2026-11-24, binding)

The I2-7 phase gate failed only because the `cov` variant runs all 430 integration cases in one process (never sharded: owner's decision in I1-T3) and that process exceeded `INTEGRATION_TIMEOUT` = 600 s; the suite grows every phase, so a whole-run limit fails again and again. **Owner: "Do not set a time limit on the overall test runs as this is a reoccurring issue. Have time limits for each test case."**

2. **Per-case time limit inside the executable**: a doctest listener (`REGISTER_LISTENER`, doctest 2.4.11 reporter interface, never edit `doctest.h`) in new `support/CaseWatchdog.{h,cpp}`, linked into `ffb_integration_tests` only. On `test_case_start` it arms a watchdog for that case; on `test_case_end` (and for subcases / reentry as doctest calls them: check the interface) it disarms. If a case runs longer than the limit, the watchdog prints one line to stderr `CASE TIMEOUT <seconds> s: <case name> (<file>:<line>)`, flushes, and terminates the process with a distinct exit code (choose one, document it) via `std::_Exit` (no destructors: a hung case cannot be unwound). Implementation: a host `std::thread` with a condition variable and steady clock, independent of the simulated time and of `HostRtos` (it must also fire when the case hangs inside the fake kernel or a busy loop). Portable C++ (MinGW / Linux), no sanitizer conflict (check ASan / UBSan / TSan-free: the thread only reads an atomic deadline).
   - **Limit**: from the environment variable `FFB_IT_CASE_TIMEOUT_S` (integer seconds; `0` = off) with a compiled default. Derive the default from measurement, not a guess: measure every case's duration (doctest `--duration=true`) in the default, m32, san and cov builds (the slowest variants), report the slowest 5 per variant, and set the default to at least 5 times the slowest case of the slowest variant, rounded up to a round number; write the measurements and the derivation in the header comment.
   - The gate passes the limit explicitly (`FFB_IT_CASE_TIMEOUT_S`) per variant, with a per-variant factor only if the measurements show it is needed (document).
3. **Gate handling of a case timeout**: a shard that ends with the watchdog's exit code is a dead shard as today (its unrun cases are run alone, the timed-out case itself is identified from the `CASE TIMEOUT` line); the timed-out case is run alone once; timing out alone = a failure of that case, reported by name (`<variant>: case timed out: <name>`); passing alone = recorded in `rerun_passed` with the reason "timeout in shard". The `cov` variant (one process): a case timeout there is a failure (as any `cov` failure: it stands), reported by name. A process that dies without the watchdog line keeps today's dead-shard handling. A missing summary or zero cases run stays a failure. Evidence: add `case_timeout_s` (the limit used) per variant and `case_timeouts` (list of case names) to the evidence.
4. **`--serial`** keeps today's command sequence except that it no longer passes a process timeout (it uses the per-case limit through the environment).
5. **Tests** (`test_it_gate.py`, stdlib `unittest`, the existing injected-runner style): no `timeout=` passed for integration runs in any mode (sharded, alone, cov, serial); the environment carries `FFB_IT_CASE_TIMEOUT_S`; a shard ending with the watchdog exit code and a `CASE TIMEOUT` line -> dead shard, the named case rerun alone, failing alone -> variant failure naming the case, passing alone -> `rerun_passed` with the reason; `cov` case timeout -> failure; evidence fields. Self-tests of the watchdog in `claude/cases/test_f1_support.cpp` (name prefix `support:`): it must not fire for a case below the limit; a death test for firing is not possible in doctest, so prove the firing path with a small helper the gate test can run: e.g. a hidden case (doctest `skip()` decorator, run only with `--no-skip -tc=<name>` by a Python test in `test_it_gate.py` or a ctest entry) that sleeps on the host clock beyond a 1 s limit set through the environment, and assert the exit code and the stderr line. Keep any such test out of the normal integration run (skipped by default) and document how it is excluded from `ffb_integration_tests`'s counts.
6. **README** (integration section) and the gate's `--help`: describe the per-case limit, the variable, the default and its derivation, and that there is no whole-run limit.
