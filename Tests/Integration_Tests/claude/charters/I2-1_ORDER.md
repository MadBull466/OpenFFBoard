### What to build

1. **`IntegrationFixture::rebootKeepingFlash(uint32_t budgetMs = 20000)`**: a simulated power cycle. Copy the flash map (`HostPlatform::flash()`), tear the chain down exactly as the fixture's destructor / `resetAll()` does (main class, USB device, threads, scheduler, fakes, chips: state what is reset and what is not), restore the flash map, and bring the chain up again through the real `cppmain` path (`bringUp`'s sequence, including USB enumeration and the driver start), returning the bring-up time like `bringUp`. Anything the chips or pins must look like after a power cycle (registers back to their reset values, supply present as before, ENABLE_IN as before) is set the way `bringUp` sets it on a fresh start; write in the header which state survives (flash only) and why that models a power cycle (RAM lost, flash kept). Derive the destruction order from the existing code; cite bug 24 (`IT_DELETES_FFBHIDMAIN`) in the comment: every case that calls it carries that macro. Note that a stored configuration may change what bring-up reaches (for example a stored motor type changes the driver's start path): `rebootKeepingFlash` must not assume the fresh-flash end state; it runs the same bounded bring-up and reports a fixture fault (`firstFault()`) if Running is not reached in the budget, so a case can see that explicitly. If `bringUp` has fresh-flash assumptions built in, factor them so both paths share one sequence without changing `bringUp`'s results.
2. **E-stop wrappers** `pressEstop()` / `releaseEstop()` (and `estopPressed()`): drive the E-stop pin as the board does (`HostTarget::setPin` on the E_STOP port / pin, then `HostTarget::triggerExti(E_STOP_Pin)`; active low: find the polarity in `FFBHIDMain.cpp:332-355` and the target header, cite the lines). The firmware ignores edges within 1000 ms of the last accepted one (`HAL_GetTick() - lastEstop > 1000`): the wrapper reports a fixture fault for an edge inside that window counted from the last edge the wrapper sent; find out whether the first press after start-up is also subject to it (`lastEstop`'s initial value and the tick at the end of bring-up) and document the answer in the header with the source line. The wrapper does not advance time itself.
3. **`support/ChipEventLog.{h,cpp}`**: an ordered record of driver events for one chip, attached to a fixture: every register write the chip receives (from `FakeTmc4671::onWrite`, or from `log()` if that is the only way: say which and why), each with simulated time (us), address, data, and the level of the driver enable pin (`HostTarget::outputPin(DRV_ENABLE_GPIO_Port, DRV_ENABLE_Pin)`; port / pin names from the target header) sampled at that write; plus an entry whenever the enable pin level differs from the last recorded one, sampled at the end of every scheduler step (`ChainScheduler::stepEndHook` or the equivalent; a pin change between two writes in the same step is then seen at the step end, after those writes: document this resolution limit). Query helpers that the I2 tests need: first index of a write to an address (optionally with a predicate on the data), "every 0x64 write before event i has torque 0 and flux 0" (decode DS 0x64: flux [15:0], torque [31:16]), the 0x1A value in force at an index, the enable level at an index. Attaching must not disturb an existing `onWrite` user of the same chip (check whether the fixture or `PositionScript` already use the hooks; if a chip supports only one hook, chain them, and say how). Detach on destruction.
4. **`armSpiFailure(chip, address, bool onWrite, HAL_StatusTypeDef status)`** (fixture or `ChipEventLog`, your choice): fails exactly the next blocking SPI transfer that carries the given register access, with `HAL_ERROR` or `HAL_TIMEOUT`. Find out how `HostTarget::spiFailNextBlocking(&hspi1, ...)` decides which transfer fails and whether a chip hook runs before or after the HAL call of the same frame: if a hook on the register cannot arm the failure for that same frame, arm it for the frame by counting transfers, or report the limit and the nearest exact alternative. The self-test proves which frame failed (from `spiTransfers` / the chip log), and that the following frames succeed.
5. **`runCommandOnWrite(chip, address, std::string cdcLine)`**: once, when the chip next receives a write to `address`, run the given CDC command (forced interleaving for F1-T6; the scheduler is cooperative, so this is the only way to put a command between two frames of the FFB thread). Find out whether running the command processor from inside a chip write hook is possible without re-entering the SPI semaphore held by the writing thread (`TMC4671.cpp:2529-2581`, `takeSemaphore` / `endSpiTransfer`); if a command that itself writes a TMC register would deadlock or be refused when run inside the hook, implement the nearest model that is still a real interleaving (for example: the hook marks the point and the command runs right after the current frame completes, before the FFB thread's next frame) and state exactly which interleaving the helper produces. Never call firmware internals directly.
6. **Self-tests** in `claude/cases/test_f1_support.cpp` (name prefix `support:`, `IT_DELETES_FFBHIDMAIN` where the chain is brought up):
   - reboot keeps a flash value written by a real command plus `sys.save` (the save command is registered at `FFBoard/Src/SystemCommands.cpp:49`) and loses a setting that was changed by command but not saved (read both back over CDC after the reboot); a second reboot in the same case also works; the existing chips / scheduler state is fresh after the reboot (for example the FFB cycle counter and the chip log start again: state which);
   - the E-stop wrapper: a press is seen by the firmware (observable through a real command or the chip: torque 0 / enable pin low), an edge inside 1000 ms is a fixture fault, a release after the window is accepted;
   - the event log: order and contents on the known bring-up sequence (the 0x64 = 0 and 0x1A writes of `TMC4671::initialize` / `initializeWithPower`, `TMC4671.cpp:300-301`, `:423-424`, the enable pin going high), and a coexisting `PositionScript` still works;
   - SPI failure: only the armed frame fails, for a read (0x6B) and for a write (0x64), for both statuses;
   - mid-write command: runs exactly once at the stated point, and its effect is visible.
   These are helper self-tests: they do not assert intended firmware behaviour of the I2 requirements (that is for I2-2 to I2-6). If a self-test runs into a firmware defect, do not write a `KNOWN_ISSUE` here: work around it in the self-test and report it under "Findings for later WOs" with file:line.
7. **`integration.cmake`**: add `ChipEventLog.cpp` to the support sources only.
8. **`Firmware/Tests/README.md`**: in the integration section, one short paragraph per new helper (what it does, its resolution / limits), next to the I1 helpers.
