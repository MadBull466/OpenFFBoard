# Common part of the I2 work orders run in parallel (I2-2, I2-3, I2-4, I2-6; owner's start 2026-11-24)

Every I2 writer order includes this text. Four writers run at the same time in the one shared checkout on `add-test-suite`, each on its own new case file.

1. **Read first** (in addition to the order's own list): `CLAUDE.md` (rules, "Integration track"), `Firmware/Tests/README.md` (integration section, especially the I2 helpers `rebootKeepingFlash`, `pressEstop` / `releaseEstop`, `ChipEventLog`, `armSpiFailure` / `armSpiTimeoutAfter`, `runCommandOnWrite` and their limits), `Tests/Integration_Tests/claude/charters/I2_WORK_ORDERS.md` (**the rules common to I2 and, through them, the ten rules common to I1 apply to you**; your WO's row), the charter `Tests/Integration_Tests/claude/charters/F1_TMC4671_CHAIN_REQUIREMENTS.md` (group G-T / G-P, "Oracles", candidate seams), `Tests/Integration_Tests/claude/plans/PROGRESS.md` (registers IB 1-37 / INR 1-32, decisions log, especially 2026-11-24 on the I2-1 helper limits), `Tests/Integration_Tests/claude/plans/HANDOFF.md` (set `axis.0.power` and `axis.0.fxratio` first because of IB 7 / bug 23; never a REQUIRE inside an INFO / CAPTURE expression: doctest deadlocks; attach a `ChipEventLog` after any `TorqueTrace`). Helpers, read-only for you: `Firmware/Tests/Integration_Tests/support/{IntegrationFixture,ChainScheduler,FfbHost,PositionScript,ChipEventLog,PidReportBuilder}.h`; examples: `claude/cases/test_f1_support.cpp` (I2 helper self-tests), `claude/cases/test_f1_hid.cpp` (create, send, observe an effect), `claude/cases/test_f1_axis.cpp` (LateFixture, supply and readiness cases; copy patterns into your own file, never include or edit those files).
2. **Your file only**: you may create or edit only the file in your `Tests/Integration_Tests/claude/charters/wo/<ID>.files`. Other writers edit other files in the same tree at the same time: never edit, format, stage, revert or "fix" a file outside your list. **Support code is not yours**: a missing helper is written as a minimal local helper in an anonymous namespace of your file; if that is impossible (it needs a change of shared or support code), stop and report under "Lead decision needed". No code under `Code_Coverage/`, `support/` or the firmware may change.
3. **Gate**: `python3 -B Firmware/Tests/Integration_Tests/tools/it_gate.py --wo <ID> --variants default,m32 --own-build` (your own build folders `../ffb-test-build/it-<ID>-<variant>`; your WO changes only a case file, so the gate runs only your file's cases). Changed files of the other active WOs appear as `other_active`: expected. If the build fails in a file that is not yours, re-run up to three times a few minutes apart and report it if it persists; never touch that file. Write cmake / build paths literally (the hook does not expand shell variables). Check in your evidence that `rerun_passed` and `dead_shards` are empty; a case that passes only alone is a state leak to fix. Stage nothing, commit nothing: the lead commits after an `--isolated` gate.
4. **Oracles**: PID 1.01 (`Tests/Code_Coverage/shared/specs/USB_PID1_01.pdf`), the TMC4671 datasheet (`TMC4671-LA_datasheet_Rev2.07.pdf`: register layouts 0x1A, 0x5D, 0x5E, 0x63, 0x64, 0x6B, 0x76), MATH written out in a comment. Behaviour fixed only by the firmware (start-up order details, recovery after a stop, timing of slow checks, values from firmware constants) is `characterization:` with `// INR <ID>/<k>: ...` (rule 6 of the I2 rules for recovery). Safety properties that need no firmware constant are plain tests: torque 0 at the chip while stopped, enable pin low, PWM off (0x1A), no non-zero torque before the driver is enabled.
5. **Defects**: confirm in the firmware source (file:line) and with a failing test of the intended behaviour: `KNOWN_ISSUE("(IB <ID>/<k>) ...")` with `REQUIRE_CHAIN_MODELLED()` right before the defect assertion (first failing assertion = the defect; check in both builds). A known bug: `(IB <ID>/<k>; same as bug <m>)` for a coverage bug (search `Tests/Code_Coverage/claude/reports/BUG_REPORT.md`), or cite an integration bug by its number, e.g. `(IB 17) ...` (search `Tests/Integration_Tests/claude/reports/BUG_REPORT.md` and the PROGRESS register first). The lead assigns final numbers.
6. **Every case**: `IT_DELETES_FFBHIDMAIN`, bring-up through the fixture, `setSpiFrameUs(0)` after bring-up unless the case is about frame time, one behaviour per case, name `F1-<id>: <statement>` or `characterization: [F1-<id>] <statement>`; equal results in default and m32 (flag any float-to-int conversion that can go out of range for a reachable setting: F1-B2 input). Cases that depend on the tick (E-stop debounce: the first press needs tick > 1000; the TMC thread's 2 s checks) advance the clock by a period derived from the cited source line, never by a tuned value. Run your file's cases once with `-s` under `timeout -s KILL 600` from your own build folder, to a file, and every new case alone under `timeout -s KILL 90` (report any that does not finish).
7. **Report**: write a short status to `/tmp/claude-1000/-mnt-SATA-SSD1-OpenFFBoard-Testing-OpenFFBoard/4de283e1-6ca1-40fb-8fd7-ddbecc886c3d/scratchpad/<ID>_status.md` early and keep it current. Within about 10 turns of your turn limit, stop and deliver your report (partial if needed). Answer format: your file with a one-line summary; per requirement the cases and their oracle; the observed values that matter; every `KNOWN_ISSUE` / `characterization:` case with its provisional label and firmware evidence (file:line); float-to-int conversions noticed; "Findings for other WOs"; anything under "Lead decision needed". The last line must be the gate's last line exactly as printed.
