## TDC: text commands (R1, R5.1-3, R5.10)

- Run commands through the public interface (`CommandHelpers.h`: `run` / `get` / `getAt` on the bridge as a `CommandHandler`, or `command()` with a `ParsedCommand`; resolve the ids by name through the registered list, never by the enum numbers). Check replies and the register traffic at `chip1` (the D1 tests show how to read the SPI frame log and the register file).
- R1.1: the seven registered commands with their flags; R1.2: every command with every type of the charter table (the register effect of `torque`, `pos`, `velocity`, `mode`, `openloopspeed`, `openloopspeedpwm`, `reg`); `torque set` starts the motor first only when the state is not `Running` (use `reachRunning`-style helpers of `TmcFixture` on the bridge's driver if reachable through the public interface; if not, say so under "Changes needed" instead of reaching into private members); R1.3: wrong types -> `ERR`, unknown id -> `NOT_FOUND`, no register traffic; R1.4: `mode` get / set / out-of-range / help text (C for the string); R1.5: `reg getat` uses `val`, `setat` uses `adr`,`val`; R1.6: `openloopspeed` / `openloopspeedpwm` set and setat (accel 100 / 10, `true` / `false`) and the identical plain `set` (R5.1: `characterization:` unless the registers show a difference); R1.7: help strings (C).
- R5.2: `mode set` with a negative value and with 7 (an unnamed mode): measure what happens (run with `--no-skip` under UBSan); if the result is wrong or UB, `KNOWN_ISSUE` / `KNOWN_ISSUE_UB` of the intended behaviour (rejected like an out-of-range value, help text reply, mode unchanged); report the evidence. R5.3: nothing else reads `Buf[0]` for length 0 (that is TDF's file; here only the command side). R5.10: only a note in the header.

## TDF: binary frames (R2, R4.1-R4.3)

- Use `TmcDebugFixture::frame / send / sent / clearSent / cdcWrites / cdcFlushes`. Replies are compared byte by byte with hand-built expected arrays; the checksum of a reply is the 8-bit sum of the first 8 bytes (TMCL 2.2): compute it in the test with `TmcDebugFixture::sum8`, not from the firmware.
- Plain tests (spec): the checksum rule (R2.2), the reply layout (R2.4: `{2, 1, 100, cmd, value MSB first, checksum}`), cmd 10 / 0x0F opcode numbers and layout (R2.8), cmd 0x88 type 0 format (9 bytes, host address 2 first, 8 characters, no checksum) and type 1 normal layout (R2.9), routing by length / first byte (R2.1), one 9-byte write plus one flush (R2.11), the register read / write reaching the fake chip with the big-endian value (R2.5, R2.6 for the chip side).
- `characterization:` (not in the specs): the opcode numbers 148 / 146 / 143, the echo of request bytes 3..6 for 146, the replies of 143 for type 3 and 4, the GGP type values (type 5 -> 2, type 2 -> 1, others 0), the GIO type 5 voltage (`getIntV() / 100`, hand-derived from the fake ADC counts of `TmcFixture`: state the derivation in a comment), the version string content `"0015V307"` and the binary bytes `0,15,3,7`, R2.12 (short CDC buffer), R4.1 (a frame split over two calls is not reassembled).
- `KNOWN_ISSUE` (L5): R2.3 wrong checksum -> status 1 reply; R2.7 type other than 3 / 4 for cmd 143 must not reply status 0; R2.10 unknown command -> status 2 reply, cmd 136 with a type other than 0 / 1 -> status 3 reply (what the intended reply carries in the value field: the spec says nothing; assert only status, command number echo and layout). Separate plain tests that those cases cause no register traffic and are not passed on to `FFBoardMain` (R2.1 / R2.10).
- R4.2: valid frames after an invalid one still work; R4.3: the register access of a valid frame reaches the chip in the driver states `Shutdown` and `Running` (use the fixture helpers, no deadlock under the fake kernel).
