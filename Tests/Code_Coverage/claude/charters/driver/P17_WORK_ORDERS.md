## MHD: `MidiHandler::midiRx` and `tud_midi_rx_cb`
- R2: decoding tests call `probe.midiRx(0, packet)` directly (fast, no USB) with a `MidiProbe` in a `MidiFixture` (no `startAndEnumerate` needed; take the packets from the USB class definition table 4-2 and the MIDI status table). Every hook with every channel 0..15 where it matters (a loop over channels is one behaviour), note on with velocity 0 / 1 / 127, note off with release velocity, control change, program change (byte 3 ignored), pitch bend table (`00 40` = 0, `00 00` = -8192, `7F 7F` = +8191, `01 00` = -8191, `00 01` = -8064: HD `(msb << 7 | lsb) - 8192`), the real-time clock on several cables, SysEx start / data / end packets of table 4-2 (`otherPacket` with the exact bytes, no note hook), system common, poly pressure, undefined status bytes, channel pressure (`characterization:`), cable number ignored (`characterization:`), R2.7 `KNOWN_ISSUE B-MIDI-3` for the three packets `p6 02 F7 00`, `p7 02 03 F7`, `p6 F0 F7 00` (one test each, the first failing assertion is `sysex()` still true), R2.11 `KNOWN_ISSUE B-MIDI-4` (the three CIN F packets of the unparsed stream), R2.13 LED pulse (`HostPlatform` LED counters, `sysPulses`). R2.12 is tested in MMN, not here.
- R3: through USB (`startAndEnumerate`, `sendPackets`): one transfer of several packets arrives in order with the interface number 0 and the exact bytes; handler destroyed then packets sent: nothing delivered, no crash, no fixture fault; second handler replaces the first, destroying the first clears the pointer (`characterization:`); R3.4 B-MIDI-6 (see the common rules: experiment first); R3.5 a burst of 17 packets (68 bytes: two transfers, 64 + 4 bytes; look how `sendOut` splits) is delivered completely and in order, and a second burst works afterwards. Also: packets delivered while the probe does not read nothing special (the probe always reads in the callback).
