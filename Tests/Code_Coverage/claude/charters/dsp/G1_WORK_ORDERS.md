- Requirements per unit (charter):
  - **C1** every ARM test id of the unit: load ARM's input and reference with `dsp::loadPattern`, run the function exactly as ARM's test does (same block size, same arguments), assert ARM's SNR threshold (`dsp::snr`, double) AND the per-sample bound (`closeAbsRel` for floats, `withinLsb` for q types), `exactEqual` for integer outputs such as shift values. Use ARM's tolerance unchanged (L4). If ARM comments out / disables an id, still run it: if it passes within ARM's tolerance, a plain test; if not, do not invent a bug: report it under "Lead decisions needed" with the measured SNR / worst sample.
  - **C2** vector functions (vexp, vlog, vinverse, add, abs): output in a `dsp::GuardedBuffer`, guard intact; block sizes 0, 1, 3, 4, 5 and 9 (unroll tail, ARM_MATH_LOOPUNROLL works in 4s): every written sample correct (reference by DEF in double), nothing written for size 0. Scalar-output functions (sin, cos, sqrt, divide, atan2): the output variable only (no guard test needed, but sanitizer builds must stay clean).
  - **C3** where ARM has no pattern: DEF (std:: functions in double) with a tolerance derived in a comment (from the type's resolution and the method's documented accuracy, e.g. table interpolation error).
  - **C4** documented edge behaviour from DOC: e.g. sqrt of a negative -> `ARM_MATH_ARGUMENT_ERROR` and output 0; divide by zero -> the documented status and saturated output; log of 0 / negative / denormal, exp overflow; atan2 of (0,0) and of the four axes / quadrants; sin/cos at the range ends of the q-type input (0 and the most negative / most positive value); results saturate rather than wrap where DOC says so. Quote the DOC sentence in a comment. If DOC is silent, a `characterization:` test is allowed ONLY for well-defined, non-suspicious results, and it must be listed in the report (it becomes a NEEDS REVIEW item).
  - **C5** (q31, q15, f16, f64 work orders) the function agrees with the f32 (or double DEF) result of the same input after conversion, within the type's resolution: derive the bound in a comment.
  - **C6** host-vs-target comment where relevant (portable C path, no ARM_MATH_DSP; float->int out of range; signed shifts; FMA contraction).
- Suspected vendor bugs (library contradicts PAT, DOC or DEF beyond a justified bound): `KNOWN_ISSUE("B-Dn: ...")` with the INTENDED result, first failing assertion = the defect, no FAIL/REQUIRE before it; UBSan finding -> `KNOWN_ISSUE_UB`; crash -> `doctest::skip` + "KNOWN ISSUE (crash)". Use ids `B-D<WO>-<n>` (e.g. `B-DF4-1`); the lead renumbers them. NEVER assert a value you suspect is wrong without a marker, and never copy the library's current output into an assertion (not even as characterization) unless DOC/DEF agrees.
