## Scope (my decision 2026-11-04)

All public functions and all data types (f64, f32, f16, q31, q15, q7 where they exist, including `*_init_*` functions and inline header functions) of the CMSIS-DSP modules the firmware uses:

| Module | Why in scope (firmware call) | Units (function x type) |
|---|---|---|
| FastMathFunctions | `arm_sin_f32`, `arm_cos_f32`, `arm_sqrt_f32` | 25 |
| ControllerFunctions | `arm_pid_init/reset_f32`, `arm_pid_f32` | 19 (incl. sin_cos, Clarke/Park and their inverses) |
| InterpolationFunctions | `arm_spline_init_f32`, `arm_spline_f32` | 12 |
| StatisticsFunctions | `arm_std_f32` | 93 |
| FilteringFunctions | `arm_biquad_cascade_df1_init_f32`, `arm_biquad_cascade_df1_f32` | 116 |
| BasicMath helpers used by the above | `arm_abs_q15/q31`, `arm_add_f32/f16` | 4 |
| CommonTables | data used by the above | via the functions |

Not in scope (unchanged): the other CMSIS-DSP modules (Matrix, Transform, Complex, Distance, Quaternion, SVM, Bayes, Window, Support beyond the helpers), the Helium/MVE and Neon variants, `ComputeLibrary`, `dsppp`, the Python wrapper, CMSIS core.

## Sources (oracles)

| Code | Source |
|---|---|
| PAT | ARM reference patterns shipped with the library, `Firmware/Libraries/CMSIS-DSP/Testing/Patterns/DSP/<Module>/<Suite>/*.txt` (generated by ARM's `Testing/PatternGeneration/*.py` with numpy/scipy in double precision). Cite as `PAT <relative path>`; the matching ARM test (`Testing/Source/Tests/<Suite>.cpp`) gives which file is input / reference / config and the tolerance. |
| ARMTOL | ARM's tolerance for that suite (`Testing/Source/Tests/*.cpp` defines: SNR threshold on the block and per-sample abs/rel or LSB bound), cited with file:line. |
| DEF | Mathematical definition (e.g. PID difference equation, Clarke/Park transforms, variance with n-1, natural cubic spline), evaluated independently in the test in double precision or hand-derived in a comment. |
| DOC | The function's documentation comment in `Include/dsp/*.h` / the source (Doxygen text written by ARM: e.g. argument error codes, saturation, scaling, Q formats). |
| LIB | The library's own behaviour only: `characterization:` + NEEDS REVIEW. Never used as an oracle otherwise. |

## Requirements (apply to every in-scope unit; each test name carries the requirement id and the unit, e.g. `[C1 arm_biquad_cascade_df1_q15] ...`)

| Id | Requirement | Oracle |
|---|---|---|
| C1 | **Reference result:** for every ARM test of the unit, the output over the ARM input matches the ARM reference pattern within ARM's tolerance (SNR over the block AND the per-sample bound; exact for integer/index outputs such as min/max index). | PAT + ARMTOL |
| C2 | **No write past the output:** guard words after every output buffer stay untouched (ARM's tail check), and the function does not read past its input (sanitizer builds). | ARM framework rule; DEF |
| C3 | **Independent check where ARM has no pattern** (Controller, sin_cos, Clarke/Park, natural spline, `*_fast_*` and 32x64 biquad variants, init functions, tests ARM disables): result vs DEF within a tolerance derived in a comment (from the data type's resolution / documented accuracy). | DEF / DOC |
| C4 | **Documented edge behaviour:** argument errors and return codes (e.g. `arm_sqrt_*` of a negative value returns `ARM_MATH_ARGUMENT_ERROR` and 0, length/size checks of init functions), saturation of fixed-point results (q7/q15/q31 saturate, do not wrap, where DOC says so), block size 0 / 1, state continuity across consecutive blocks for stateful functions (filters, PID). | DOC / DEF |
| C5 | **Type consistency:** the q-type and f16/f64 results agree with the f32 result of the same input after conversion, within the type's resolution (catches a wrong scale/shift where ARM has no pattern of that type). | DEF (hand-derived tolerance) |
| C6 | **Host vs target:** a test whose result can differ on Cortex-M (ARM_MATH_DSP intrinsic path absent on the host, FMA contraction, out-of-range float->int, signed shifts) says so in a comment; UBSan findings in vendor code are `KNOWN_ISSUE_UB` with a vendor bug number. | CLAUDE.md |

A finding where the library contradicts its pattern, its DOC or DEF is a **suspected vendor bug** (`KNOWN_ISSUE` / `KNOWN_ISSUE_UB` / skipped crash, ids B-D1.., global "V" numbers in `Tests/BUG_REPORT.md` at the end of each group). Loose ARM tolerances or questionable ARM tests are NEEDS REVIEW items, not bugs.

## Infrastructure (G1, built by a worker, reviewed by the lead)

* **Executable `ffb_dsp_tests`** (own CMake block, own ctest entry, `FFB_DSP_TESTS_EXCLUDE` / `_SANITIZE`, in `test_report` / `run_all_tests.py`, own coverage tier "dsp" in `coverage_report.py`, not in the ladder): links the in-scope CMSIS-DSP sources of all types; built only when the DSP submodule (incl. `Testing/Patterns`) is present (`FFB_TESTS_USE_DSP`). The four existing executables keep byte-identical compile commands; the 53 existing tier C cases in `ffb_target_tests` stay as they are.
* **Defines:** the same as the existing DSP builds (`ARM_MATH_LOOPUNROLL`, `__GNUC_PYTHON__`: portable C path, no intrinsics) so results are comparable; f64 compiles as is.
* **f16 (lead decision L2):** compiled only into `ffb_dsp_tests`, with `-D__ARM_FP16_FORMAT_IEEE=1 -D__fp16=_Float16` on the f16 sources and the f16 test files, behind a CMake feature check (the compiler supports `_Float16`); without support (e.g. some MinGW) the f16 tests are not built and the configure output says so. No firmware or vendor file is edited.
* **Pattern loader** `support/DspPatterns.h` (+ its own tests): reads a pattern file at runtime from `FFB_CMSIS_PATTERN_DIR` (CMake define, absolute, forward slashes), parses the type letter, count and the hex lines (never the `//` comments), returns typed vectors (f64/f32/f16 by bit pattern, q31/q15/q7 two's complement); a missing file fails the test (not a skip); CRLF tolerant. Comparison helpers: SNR in double, per-sample abs/rel and LSB bounds, guard-word check.

## Lead decisions

* **L1** The five inventory questions are answered by my scope decision: Statistics is in (the firmware calls `arm_std_f32`); all of Filtering is in; Controller `sin_cos`, Clarke/Park are in (functions of an in-scope module; oracle DEF); the patterns are read directly from the submodule at run time (nothing copied under `Firmware/Tests`).
* **L2** f16 build switch as above (tests-only compile defines, feature-checked).
* **L3** The host runs the portable C code path (`__GNUC_PYTHON__`, no `ARM_MATH_DSP`); the Cortex-M intrinsic path is not tested (host-vs-target caveat in every report).
* **L4** ARM's tolerances are taken as they are; a tolerance that looks too loose (e.g. FastMath q31 sin/cos 2200 LSB, biquad f64 rel 1.2e-3) gets an additional DEF-based tighter check only if a hand derivation justifies the bound; otherwise NEEDS REVIEW.
* **L5** Suspected vendor bugs: ids B-D1.., become global vendor numbers (V37 onwards) at the end of each group.
