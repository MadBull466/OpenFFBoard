## Hard rules

Never modify any other file under `Firmware/` (including the Makefile, ARM build, `Firmware/Libraries/`, TinyUSB, `eeprom.c` and other vendor code) unless I explicitly ask. - Never edit the firmware sources to make them testable and never add `#ifdef` for tests to them. Use a test double in `fakes/` or a stub in `platform/src/host_stubs.cpp`.
- New tests, fakes, mocks and CMake changes go in `Firmware/Tests/` only, matching the existing structure and naming.
- Use doctest. Do not introduce a new test framework. Python tests use stdlib `unittest` (do not install pytest).
- Git: work on branch `add-test-suite`. Local commits are allowed (small and frequent). Pushing is allowed ONLY to the user's fork `https://github.com/MadBull466/OpenFFBoard` (branch `add-test-suite`), and only when the user asks. Push by URL (`git push https://github.com/MadBull466/OpenFFBoard.git add-test-suite`) so no remote is added. Never push to `origin` (upstream Ultrawipf), never push other branches or force-push, and never add or change a git remote. Do not change git config: use a one-off `git -c user.name="MadBull.Ben" -c user.email= commit ...` (author name `MadBull.Ben`, email deliberately empty). Never write the user's email address into any file, commit message or report. Never commit to main.
- No hardware access, flashing, serial/USB/CAN, or network access during tests.
- Ask before adding any dependency that has to be downloaded (e.g. CMake FetchContent). Do not install anything globally.
- Keep the existing tests: all 318 baseline cases (names in `Firmware/Tests/Code_Coverage/baseline/test_cases.txt`) must stay present with unchanged results. Never edit existing test files; add new files. After every CMake or test change, rebuild and run `tools/check_baseline.py`; `ffb_unit_tests` must report 0 failed (on GCC 16 the whole executable gives 654 passed, 0 failed, 4 skipped with the documented exclusion; the 318 baseline cases alone give 316 passed, 2 skipped, checked by `tools/check_baseline.py`).

## Test scope
- In scope: firmware logic outside `Firmware/Libraries/`, plus vendor code in these tiers:
  - Tier A: `eeprom.c` (directly, via flash tests on a fake flash with real NOR semantics), the FreeRTOS C++ wrappers (`c*.cpp`), the two Python helpers.
  - Tier B: TinyUSB device code in `Firmware/FFBoard/USB/`, tested against a fake USB controller.
  - Tier C: the CMSIS-DSP functions the firmware calls (biquad, spline, whatever `EffectsCalculator` and `Filters` use; 10 functions, 100 %). Since P11 every function of the CMSIS-DSP modules the firmware uses is tested (`ffb_dsp_tests`, see `Tests/Code_Coverage/claude/plans/COVERAGE_AND_SCOPE.md`).
- Not tested: ST HAL, CMSIS core, the FreeRTOS kernel, `Firmware/Targets/**` and CubeMX-generated code.
- Driver track (added 2026-11-02): the driver code for **TMC4671, ODrive and VESC** is now IN scope, in that order, and is driven by `Tests/Code_Coverage/claude/plans/DRIVER_TEST_PLAN.md`. Only those three drivers (plus `TMCDebugBridge`, see P13 below).
- P13 (added 2026-11-10): `TMCDebugBridge` is now IN scope, driven by `Tests/Code_Coverage/claude/plans/P13_TMCDEBUGBRIDGE_PLAN.md`. Its feature macro `TMCDEBUG` is on in `ffb_driver_tests` only (off in every other executable). TMCL values specified in the supplied documents (`Tests/Code_Coverage/shared/specs/TMCL_reference.pdf` and the TMC4671-TOSV-REF / LEV-REF manuals: frame, checksum, reply layout, status codes, GGP / GIO / version command) are plain tests; TMCL values they do not specify (opcodes 143 / 146 / 148, parameter meanings, version content) are `characterization:` tests; the bridge's silent drops of invalid frames are `KNOWN_ISSUE` (owner's decisions 2026-11-10).
- P14-P17 (added 2026-11-10): the PWM (`MotorPWM.cpp`, P14), SimpleMotion (`MotorSimplemotion.cpp`, P15), MyActuator (`RmdMotorCAN.cpp`, P16) drivers and MIDI (`MidiMain`, `MidiHandler` and the TinyUSB `class/midi` code, P17) are now IN scope, one phase each in that order, driven by `Tests/Code_Coverage/claude/plans/P14_P17_REMAINING_DRIVERS_PLAN.md`. Executables: PWM, SimpleMotion and MyActuator in `ffb_driver_tests`, MIDI in `ffb_usb_tests`; each feature macro (`PWMDRIVER`, `SIMPLEMOTION`, `RMDCAN`, `MIDI`) is turned on in that executable only and stays off in every other one. Specs: `Tests/Code_Coverage/shared/specs/CAN_BUS_Motor_Motion_Protocol_V4.3.pdf` for MyActuator. SimpleMotion: `Tests/Code_Coverage/shared/specs/SimpleMotionV2-master/` (protocol docs and reference library source, never committed). MIDI: `Tests/Code_Coverage/shared/specs/midi10.pdf` (USB Device Class Definition for MIDI Devices 1.0) and `Tests/Code_Coverage/shared/specs/MIDI_1.0_Detailed_Specification.pdf`. The firmware's TinyUSB class uses USB-MIDI 1.0 descriptors, so the 1.0 documents are the oracle (`USB MIDI v2_0.pdf` is no longer needed; where the 1.0 documents do not specify a byte, `characterization:`). PWM needs no protocol spec. New fakes (timer / PWM output, UART if missing) go under `fakes/` with the fidelity header. Stop at the end of every phase.
- Fake any driver that is not yet in scope or not built into the executable under test at its interface (`MockMotorDriver`, `MockEncoder`). Test only the in-scope caller (correct calls, arguments, ordering, handling of return values and errors), never the driver internals.

## Test conventions (from `Firmware/Tests/README.md`)
- Use a fixture. It resets the global state so tests do not depend on order.
- Test through public interfaces (reports, commands, class interfaces), not private members.
- One behaviour per test case. The name is a statement that is true if the test passes.
- Never sleep. Advance the simulated time (`HostPlatform::advanceMs`); run threads with `HostRtos::runUntilBlocked` / `runUntilIdle` or the fixtures' `process()`.
- `characterization: ...` in the test name = documents what the firmware does today where correct behaviour is unverified. Also record it as NEEDS REVIEW in `Tests/Code_Coverage/claude/plans/PROGRESS.md`.
- `KNOWN_ISSUE("...")` = test describes the INTENDED behaviour but fails because of a suspected defect (suite stays green). `KNOWN_ISSUE_UB(...)` is the same for undefined behaviour and is skipped in sanitizer builds. Never write a test that expects a suspected buggy result without one of these markers. In a `KNOWN_ISSUE` test the first failing assertion must be the one that describes the defect, so `should_fail` cannot hide a different failure.
- `KNOWN_ISSUE_32BIT("...")` / `KNOWN_ISSUE_32BIT_UB("...")` (`support/KnownIssue32.h`, P18) = a suspected defect that exists only with a 32-bit `size_t`, like on the target. On the 64-bit host the case is a plain passing test; in the 32-bit build the first is should_fail and the second (undefined behaviour) is skipped. `tools/run_all_tests.py` classifies them by the build's width.
- New firmware sources: add to `FIRMWARE_SOURCES` in `CMakeLists.txt`; extend the fake platform minimally.
- Every fake documents what it models, its source (RM0090 chapter, HAL source, spec section), what it does not model, and a confidence rating, and is strict (fails the test on use the hardware would reject). See "Fake fidelity rules" in `Tests/Code_Coverage/claude/plans/TEST_PLAN.md`.
- Host is 64-bit, target is 32-bit ARM with a single-precision FPU. Flag any test whose result could differ on target: type sizes, struct packing/alignment, endianness, float vs double promotion, integer overflow, signed shifts, out-of-range float-to-int conversions.

## Known issues
- **`effectsForces` out-of-bounds read.** GCC 16's libstdc++ enables `_GLIBCXX_ASSERTIONS` at -O0, so this existing read aborts the doctest run (baseline: 192 of 317 cases ran). Exact case name: `requesting the forces of a not existing axis is rejected` (`cases/test_effects_calculator.cpp:1062`). Treat it as a suspected firmware bug. Do NOT fix the firmware. Exclude it with `--test-case-exclude=` in runs, list the exclusion in every report, and do not disable `_GLIBCXX_ASSERTIONS` globally.
- **CMSIS-DSP `arm_spline_f32` ASan finding** (vendor code, reached from `EffectsCalculator::evaluateReconstructionFilter`). Keep ASan on the whole build. In sanitizer runs skip only the two spline cases (`reconstruction of a constant signal is constant`, `reconstruction of a step never leaves the range of the input values and reaches the target`). Report it, never fix it.

- **Skipped crash.** The case `command with an unknown id is rejected` (`cases/test_command_execution.cpp:186`) stays skipped: `executeCommands` dereferences the command definition before the null check and terminates the run. Report it, never fix it.

- **32-bit build (P18) and bug 225.** `-DFFB_TESTS_32BIT=ON` (default OFF) builds every executable with `-m32 -msse2 -mfpmath=sse -funsigned-char` (ILP32 like the target). It needs gcc or clang with 32-bit multilib on Linux and fails at configure time otherwise (MSVC, macOS, no multilib). In that build only: the two existing cases `mag rejects reading an address beyond the effects` and `state rejects an address beyond the effects` are excluded from ctest (`FFB_TARGET_TESTS_EXCLUDE_32BIT`), because bug 225 (`int64_t` command address compared with `size_t` in `SerialFFB.cpp`, signed on 32 bit) makes them read out of bounds and abort the run; and 5 DSP test files that use `__int128` (`test_dsp_filt_fir_q.cpp`, `test_dsp_filt_lattice.cpp`, `test_dsp_filt_lms.cpp`, `test_dsp_filt_sparse.cpp`, `test_dsp_stats_q31.cpp`) are left out of `ffb_dsp_tests` (`test_dsp_filt_conv_q31.cpp` guards itself and has no cases there). Report bug 225, never fix it. The i386 build does not prove ARM struct layout (`int64_t` / `double` members are 8-aligned on ARM, 4 on i386) or ARM's `uint32_t` = `unsigned long`.

## Model roles (driver track)
- Opus 5.5 (`claude-opus-5-5`, effort medium) is the technical lead: ambiguous specifications, deciding what each suite must prove (the requirements charter), serious test-design disagreements, final quality control. It writes no bulk tests.
- Sonnet 5.5 (`claude-sonnet-5-5`, effort medium) does most agent work: mapping existing tests to requirements, ordinary unit tests, edge-case tests with clear expected behaviour, first-pass review for gaps and false positives.
- Haiku 5.5 (`claude-haiku-5-5`) or a script summarises large test output. Prefer a script.
- Agent definitions live in `.claude/agents/` (created in phase D0). Do not hard-code a model other than these.
- Expected values come from the spec or vendor documentation, or a hand derivation written in a comment. Never copy the value the firmware currently produces into an assertion without `characterization:` and a NEEDS REVIEW entry.
- Specification files are supplied by me under `Tests/Code_Coverage/shared/specs/` and are never committed. Do not download them. Never invent register maps, opcodes or CAN frames; if a spec is missing, stop and ask.
